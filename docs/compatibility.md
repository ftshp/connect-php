# Backward compatibility

ftshp/connect follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). This page says what the version number promises, which parts of the package the promise covers, and how the parts you may implement yourself can change.

## Versions

From 1.0.0, breaking changes go into major releases only. Minor releases add features and patch releases fix bugs, and neither breaks code that follows the rules on this page.

Before 1.0.0, a minor release (0.2 to 0.3) can contain breaking changes and a patch release (0.2.0 to 0.2.1) contains only backward compatible fixes. Require the package with a caret, such as `"ftshp/connect": "^0.2"`, which Composer reads as `>=0.2.0 <0.3.0`. Every breaking change is described at the top of its release in [CHANGELOG.md](../CHANGELOG.md), with the change to make in your code.

Before something is removed or changed in a breaking way, a release marks it `@deprecated` and, for methods, with the `#[\Deprecated]` attribute, so PHP raises `E_USER_DEPRECATED` when it is called. The deprecation names the replacement. Deprecated API keeps working until the next release that may break it: the next major release, or before 1.0.0 the next minor release at the earliest.

A release may raise the minimum PHP version or the minimum `google/protobuf` version, in a minor or major release and never in a patch release. Composer then keeps installing the older release on platforms the new one no longer supports.

## What the promise covers

Everything in the `Ftshp\Connect` namespace that is not in `Ftshp\Connect\Internal` and is not marked `@internal` is public API. For public API a release in the same version range keeps:

- every class, interface, enum, enum case, constant, method and public property, with its name;
- the parameter names of public methods and constructors, because PHP 8 named arguments make them part of every call that uses them;
- the position of required parameters, and of all parameters of methods and of constructors other than those of `Client` and `Server`;
- parameter types, which may only become wider, and return types, which may only become narrower, on classes you call;
- the documented exceptions: a failed RPC throws `ConnectException`, and invalid metadata that you set throws `\InvalidArgumentException`.

A release may add a method to a class, a public property, a class or an optional parameter at the end of a method. All classes are `final`, so these additions cannot clash with a subclass.

### Generated code

Generated code is part of the promise in two ways.

The code the plugin writes keeps its names and shapes. Namespaces, class names and method names follow the rules in the [README](../README.md#generated-code), and each method keeps the signature `method(Request $request, Context $context = new Context()): Response`. A release does not rename a generated class, a generated method or a generated file.

The runtime API that generated code calls stays as it is: the `MethodDescriptor` constructor with its six positional parameters, the `#[Service]` and `#[Procedure]` attributes, the `Idempotency` cases, `Client::unary()` and the `Context` constructor without arguments. Code that a plugin release generated works with any later runtime in the same version range.

The plugin and the library are released together under the same version tag. Code generated by protoc-gen-connect-php 0.2 needs `"ftshp/connect": "^0.2"`, and release builds of the plugin write their version into the header of every generated file, so you can tell which constraint a package needs. A package that ships generated code should require the runtime with that constraint.

Adding an RPC to a service adds a method to the generated interface, and every class that implements the interface then has to implement the new method. Package maintainers who publish generated code should treat a new RPC as a breaking change for server implementations.

### Wire behaviour

The defaults that decide what goes over the wire are covered, because changing one changes what clients and servers accept without any change in your code:

- `Client` accepts response bodies up to `maxResponseBytes` and `Server` accepts request bodies up to `maxRequestBytes`. Both default to 4 MiB (4194304 bytes) and count the raw and the decompressed body. 0 turns the limit off.
- An exception from a handler that is not a `ConnectException` reaches the client as `unknown` with an empty message.
- `Server` accepts and offers gzip, compresses responses of at least `compressMinBytes` (1024 bytes) when the client accepts it, and accepts requests without `Connect-Protocol-Version` unless `requireProtocolHeader` is true.
- `Client` sends POST unless `useGet` is true, sends uncompressed requests unless `compression` is set, and accepts gzip responses.

Behaviour that contradicts the [Connect protocol](https://connectrpc.com/docs/protocol/) is a bug. A fix can change what goes over the wire and ships in a patch or minor release, listed under "Fixed" or "Changed" in the changelog.

## What the promise does not cover

- Classes in the `Ftshp\Connect\Internal` namespace.
- Anything marked `@internal`, such as `Context::begin()`, `Headers::replace()`, `ConnectException::received()` and the constructors of `UnaryRequest` and `ServiceDescriptor`. They are public because other classes of the package call them.
- The position of the optional parameters of the `Client` and `Server` constructors. Pass them as named arguments, such as `new Server($factory, $factory, interceptors: [...])`. A release may add a new option anywhere in the list.
- A new method on an interface that is not listed below as one you may implement.
- The text of exception messages that the package creates, and the text of docblocks.
- Behaviour that is not documented, and code that depends on a bug.

## Interfaces you may implement

You may implement these interfaces:

- `Ftshp\Connect\Interceptor`
- `Ftshp\Connect\Codec\Codec`
- `Ftshp\Connect\Compression\Compression`
- the service interfaces that protoc-gen-connect-php generates

A release in the same version range does not add a method to them or change a parameter or return type, since either would break every implementation. A new capability arrives as a new interface that an implementation can add when it needs it. Streaming, if it is ever supported, would get its own interceptor interface next to `Interceptor`.

The exceptions these interfaces may throw are part of the contract and are written on each interface. `Codec::decode()` throws a `ConnectException` with `invalid_argument` for data it cannot parse. `Compression::decompress()` stops once the output passes `$maxBytes` and then throws `resource_exhausted`, and it throws `invalid_argument` for corrupt input.
## Size limits and HTTP clients that decompress

The response limit works only if `Client` sees the compressed body. It sends `Accept-Encoding` itself and inflates gzip with a bound, stopping once the output passes `maxResponseBytes`.

Guzzle, with its default `decode_content: true`, lets curl inflate the response before `Client` reads it and removes the `Content-Encoding` header. The 4 MiB limit then still rejects a large message, but only after curl has written the whole inflated body into Guzzle's temporary stream, so a small compressed response can take that much memory or disk space first. Turn decoding off in the Guzzle client you pass to `Client`:

```php
$http = new GuzzleHttp\Client(['decode_content' => false]);
```

The same applies to any PSR-18 client or plugin that decompresses responses itself. Symfony HttpClient leaves the body compressed when the request carries its own `Accept-Encoding` header, which `Client` always sends.
